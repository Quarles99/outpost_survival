# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Godot 4.7 (GDScript) base-building/survival game ("outpost survival"), inspired by State of Decay 2, Warcraft 3, Age of Empires 2, Project Zomboid, RuneScape, and Battle Brothers — grimdark medieval fantasy setting. Design notes live in `Outpost Survival Game Ideas`. The project is early-stage: a single base scene with recruitable characters who can be assigned to gathering workstations.

Renderer is `gl_compatibility` (both desktop and mobile). Main scene: `res://scenes/base/Base.tscn`.

## Running / building

This is a Godot editor project, not a CLI-buildable one. Open and run it with the Godot 4.7 editor (or `godot4 --path .` / `godot4 -e --path .` if the Godot binary is on PATH). There are no automated tests, lint configs, or CI in this repo — verify changes by running the project in the editor and exercising the affected flow.

## Architecture

**Autoload singletons:**
- `GameState` (`autoload/game_state.gd`) holds the global resource pool (`food`, `wood`) as a plain dictionary, exposes `add_resource`, `can_afford`, `spend`, and emits `resources_changed` for UI to listen to. `add_resource` clamps every resource at a minimum of 0 — this is what makes the food drain below safe to run unconditionally rather than gating it on affordability. Also tracks `population_count`/`population_capacity` (`add_population_capacity`, `population_changed`), and runs its own food-consumption `Timer` (created in code in `_ready()` — autoloads have no `.tscn`, so there's nowhere to put a scene Timer node): every `CONSUMPTION_INTERVAL` (1s) it drains `FOOD_PER_CITIZEN * population_count` food, regardless of whether citizens are assigned to a post. This is the only per-citizen cost currently modeled — there's no starvation penalty yet if food hits 0, it just stops going lower.
- `WorldGrid` (`autoload/world_grid.gd`) is the single source of truth for grid-cell occupancy and the tree registry, so buildings (via `Base`) and trees (via lumberjack replanting) can never overlap each other. `Base._ready()` calls `WorldGrid.configure(ground_origin, bounds_min, bounds_max, container)` once at startup. Exposes `grid_to_local`/`local_to_grid` (thin wrappers over `IsoUtils` plus the ground's screen offset), `is_in_bounds`/`is_free`/`reserve`/`release` (single-cell occupancy), and `plant_tree`/`find_available_tree`/`find_plantable_cell` (the tree registry). Anything that needs grid↔screen conversion or occupancy checks — `Base`'s building placement, `Character`'s lumberjack AI — goes through this rather than each maintaining separate state.

**Camera (`scripts/rts_camera.gd`, `RtsCamera` class, `Base`'s `Camera2D` child):** scroll wheel zooms (`MOUSE_BUTTON_WHEEL_UP`/`DOWN`, tweened, clamped to `zoom_min`/`zoom_max`), middle-mouse hold+drag pans 1:1 with the cursor, and the cursor sitting within `edge_scroll_margin` px of the viewport edge pans continuously every `_process`. All three consume the event in `_input()` (not `_unhandled_input()`) so they never reach `Base`'s "any mouse button click deselects/closes panels" checks — `_input` always runs before `_unhandled_input` regardless of node tree order, which is what makes that interception reliable. `Base._ready()` calls `camera.configure_limits(min_local, max_local)` using the same ground-bounds corners it feeds `WorldGrid.configure`, so panning/edge-scroll stop at the map edge (plus `limit_margin`). **`Camera2D.limit_left/top/right/bottom` only clamp the rendered view, not the `position` property itself** — code that sets `position` directly (the drag/edge-scroll handlers here) can drift `position` arbitrarily far past the limits with zero visible change, then the camera appears to "lag" for exactly that same distance before the opposite direction has any visible effect. `_clamp_position()` clamps `position` to `limit_left/right/top/bottom` manually after every drag-motion and edge-scroll update — don't add a new way of moving `position` without also calling it, or this regresses. **Non-obvious gotcha verified empirically in this Godot build:** `Camera2D.zoom` values *greater* than 1 magnify (zoom in) and values *less* than 1 zoom out — the opposite of what a literal reading of the Godot docs suggests — so the screen↔world conversions here divide by `zoom` (`screen_delta / zoom`), not multiply. If this ever looks backwards after a Godot upgrade, re-verify that assumption with an actual on-screen test before changing the math blind. The camera's initial `position` is set to `get_viewport_rect().size / 2.0` in `_ready()` specifically to reproduce the exact framing the game had before any camera existed (world origin at the viewport's top-left) — don't hardcode a fixed starting position, it needs to adapt to viewport size.

**Base scene (`scripts/base.gd`, `Base` class) is the top-level coordinator.** It owns the list of `characters` and `posts` (every placed job post - Workstation-family only; the Outpost Hall and Storage Facilities are never in `posts`, since they're never job posts). Job assignment is **fully automatic** - there is no manual assignment of any kind (no drag, no click-a-citizen-then-click-a-post, no explicit hauler assignment). `Character.clicked(self)` fires on left-click; `Base._on_character_selected()` just selects the citizen and opens their (view-only) `SkillPanel` - clicking the same already-selected citizen again deselects them, same as clicking elsewhere.
- `Base._run_job_assignment()` is the entire assignment system, re-run from scratch (not incrementally patched) on every relevant trigger: a citizen recruited or departed, a job post built/disabled/re-enabled, or a save loaded. It's citizen-proposing Gale-Shapley deferred acceptance generalized to multi-worker posts: each citizen ranks the six job skills by their own level (`SkillTitles.skill_preference_order` - stable even when every skill ties at level 1, which a naive "precompute one best skill per citizen" approach gets wrong, see that function's doc comment), then repeatedly proposes to their best not-yet-rejected skill's post pool (every post sharing a skill_id pools its capacity together); a pool under capacity accepts immediately, a full pool evicts its weakest occupant only on a *strict* level improvement (ties never swap). A citizen who exhausts every preference without landing a post stays unassigned, which `Character.assign_to(null)` already turns into automatic hauling (see Character/post interaction pattern below) - "a citizen who can't find a job becomes a hauler until one opens up" falls out of this for free, it isn't separately coded.
- Any job post can be right-clicked to toggle `Workstation.disabled` - see its own doc comment. `Base._on_post_disabled_changed()` evicts the post's current worker immediately on disable and re-runs `_run_job_assignment()` either direction.
- `Base._job_posts()` filters `posts` to ones whose `get_skill_id()` is one of `SkillTitles.TITLE_SKILLS` (the six job skills) - this is also what implicitly excludes the Outpost Hall/Storage Facility (never in `posts` at all) and a disabled post (excluded from capacity accounting, not from `posts` itself) from ever being assigned into.

**Character/post interaction pattern:** `Character` (`scripts/character.gd`) is an `Area2D` with a `CharacterData` resource (name, per-skill xp dict, happiness - stored as `.tres` files under `resources/characters/` for the 3 starting citizens, procedurally generated for recruits). `assign_to(post)` (called only by `Base._run_job_assignment()` now, never by player input) calls `post.add_worker()`/`remove_worker()`, moves the character to `post.get_worker_spot()`, and starts the matching work loop for `post`'s concrete class (`_run_farm_loop`/`_run_lumberjack_loop`/`_run_generic_work_loop`, dispatched in `_start_work()`); `assign_to(null)` moves the character home and starts `_run_hauler_loop()` instead - this is what "a citizen without a job hauls automatically" actually is, not a special case. Posts are duck-typed (every job-post class exposes `add_worker`/`remove_worker`/`get_worker_spot`/`display_name`/`get_skill_id`/`max_workers`/`active_workers` but doesn't share a base class beyond `Workstation` itself) — when adding a new assignable post type, match this interface rather than introducing a new formal base class.

**Farm (`scripts/farm.gd`) `extends Workstation`.** Despite the name it's a generic single-input/single-output converter (`output_per_tick`, `skill_id`, `sprite_tint` exported on Farm itself; `input_resource`/`input_per_tick` live one level up on `Workstation` - see below) - the original wood→food Farm and the raw-crop Alternative Crop Types (Grain Farm, Hops Farm, Fruit Orchard, Potato Farm) are all just differently-configured Farm instances sharing `Character._run_farm_loop`, distinguished only by `BuildingCatalog` fields applied at placement. Mill/Bakery/Brewery used to be Farm instances too but were carved out into their own `Workshop` class (see below) per an explicit request - "a mill/bakery/brewery isn't a farm." See `Outpost_Survival/Docs/mechanics.md`'s Gathering & Hauling section for the full loop (input buffer, output buffer, haul-trip timing) rather than re-deriving it here.

**Brickmaker (`scripts/brickmaker.gd`) `extends Workstation`** (not `Farm`) - stone→brick, training a fixed `"masonry"` skill (hardcoded, not exported, since it's the only recipe this class ever has - compare `Workshop` below, which needs a configurable skill since it covers three different trades). It reuses `Character._run_farm_loop` by structural typing alone: `input_resource`/`input_per_tick` (and `get_input_resource()`'s implementation) were moved from `Farm` up onto `Workstation` itself specifically so any converter-shaped post - not just the Farm-family - can share that loop. Deliberately does **not** extend `Farm` and has no `clicked` signal, which is what keeps it out of the Farm-family crop-selection panel (`Base._wire_farm_clicks` only wires that panel to `is Farm` nodes) - a Brickmaker is a dedicated, single-recipe building, not one of several interchangeable recipes on the same worker slot the way Cabbage Farm/Grain Farm/etc. are. `_run_farm_loop`'s water-access output bonus (`Character.WATER_FARM_OUTPUT_BONUS`, see `Outpost_Survival/Docs/stats.md`'s Water Farming Bonus table) is gated on `post is Farm` specifically so neither Brickmaker nor Workshop pick it up - a well boosting brick/flour/bread/beer production wouldn't make sense.

**Workshop (`scripts/workshop.gd`) `extends Workstation`** (not `Farm`) - the shared class for Mill/Bakery/Brewery, exactly the same relationship to `Farm`/`Character._run_farm_loop` Brickmaker has (structural typing, no `clicked` signal, not part of the Farm-family retool panel - `BuildingCatalog.FARM_FAMILY_SCENE_PATHS` only lists `Farm.tscn`/`CropStation.tscn`, not `Workshop.tscn`), except `skill_id` stays a per-catalog-entry export (like `Farm`'s) rather than hardcoded, since one class covers three distinct trades (`"milling"`/`"baking"`/`"brewing"`). Uses its own dedicated 2x2 art (a region cropped from `art/Pixel Isometric 16x16/Structures2.png`, deliberately distinct from both the Cabbage Farm's tilled-soil plot and the House's peaked roof) rather than reusing the Farm-family's sprite the way these three used to when they were still Farm instances on `CropStation.tscn`.

**Lumber Camp gathering (tree-based, not Farm's buffered converter loop):** `LumberCamp` (`scripts/lumber_camp.gd`) `extends Workstation`, adding `search_radius`/`optimal_tree_count`/`replant_per_harvest`/`wood_per_chop`/`chop_interval` exports — still duck-type-compatible as a `post`. The actual walk/chop/replant behavior is a per-character coroutine, `Character._run_lumberjack_loop()` (kicked off by `assign_to` when `post is LumberCamp`, cancelled by bumping `_work_session` so a stale coroutine notices and returns next time it resumes): find the nearest unclaimed mature `WorldTree` within `search_radius` via `WorldGrid.find_available_tree` → walk to it → chop every `chop_interval` (`WorldTree.harvest()`) until depleted → replant toward `optimal_tree_count` (via `WorldGrid.find_plantable_cell`/`plant_tree`) → repeat. `WorldTree` (`scripts/tree.gd`) starts as a small sapling (`is_mature = false`) and tweens its sprite scale up to full size over `grow_time` seconds before it's harvestable; `harvest()` shrinks/fades it out and emits `depleted` once its wood is gone, which `WorldGrid` listens for to free the cell and drop it from the registry. The class is named `WorldTree`, not `Tree` — `Tree` collides with Godot's built-in `Tree` UI control and silently fails to register as a global class if reused.

**Building/placement system:** `BuildingCatalog` (`scripts/building_catalog.gd`) is a static, `RefCounted` catalog of buildable options (id, display name, scene, cost, and — for anything placeable — a `grid_size: Vector2i` footprint). `BuildingCatalog.placeable_options()` filters to entries with `grid_size` (currently Outpost Hall, Farm, Lumber Camp, House — all 2x2 except Lumber Camp, which is 1x1); `get_option(id)` looks one up by id. The HUD's "Build" button opens `BuildMenu` with those options; picking one hands the option `Dictionary` to `Base`, which drives the whole placement flow:
- A translucent "ghost" instance of the option's scene follows the mouse, snapped to the grid, tinted green/red based on `Base._ghost_valid` (in ground bounds, free per `WorldGrid`, and `GameState.can_afford` — affordability of the *full* cost is still checked here even though nothing is actually spent yet, see below).
- Left-click confirms; right-click/`ui_cancel` cancels. Confirming does **not** instantiate the real building anymore — it reserves the footprint's cells and spawns a `ConstructionSite` (`scripts/construction_site.gd`, `extends Workstation`) via `Base._spawn_construction_site()`, tracked in `Base.construction_sites` (deliberately *not* `Base.posts` yet — see below). Three footprint-sized scenes share this one script (`scenes/workstation/ConstructionSite1x1.tscn`/`2x2.tscn`/`2x4.tscn`), picked by the option's `grid_size`. The building system (`Base._confirm_placement`/`_spawn_construction_site`/`_on_construction_materials_ready`/`_on_construction_complete`/`_materialize_building`, `Character._deliver_construction_material`/`_run_construction_loop`) has two phases:
  - **Materials.** `ConstructionSite.materials_needed` (a `resource_name -> remaining amount` `Dictionary`, seeded from the option's own `cost`) is drained by ordinary haulers — `Character._find_haul_job()` treats any site's still-needed resources as a third kind of haul job alongside a post's output pickup/input delivery, and `_deliver_construction_material()` walks a load from the stockpile to the site (this is where `GameState.spend()` actually happens, not at placement-confirm time — a site can sit half-stocked indefinitely if the stockpile runs dry, same as a starved Workstation input). A resource's entry is erased (not left at `0.0`) once fully delivered; once `materials_needed` is empty, the site emits `materials_ready`.
  - **Labor.** `Base._on_construction_materials_ready()` is the only place a site is ever appended to `posts` — before that, `Base._job_posts()` can't see it (it filters `posts`, not `construction_sites`), so nobody can be assigned to "build" a site with nothing to build with yet. Once added, it's a normal job post training the `"construction"` skill (`ConstructionSite.get_skill_id()`, part of `SkillTitles.TITLE_SKILLS`/`RecruitCatalog.SPECIALIZATIONS`/`SkillPanel.SKILL_DISPLAY_ORDER` like any other job skill) — `Base._run_job_assignment()`'s existing Gale-Shapley matching is what "preferring citizens with the highest proficiency in construction" actually is, no special-casing needed. `Character._run_construction_loop()` adds flat labor (scaled by the worker's construction-skill multiplier and the settlement happiness multiplier, no input/output buffer at all) to `ConstructionSite.labor_completed` every `work_interval` tick; `labor_required` is derived from the option's total material cost (`Base._labor_required_for`), not hand-authored per building. Reaching it calls `ConstructionSite.mark_complete()`, which emits `construction_complete`.
  - **Completion.** `Base._on_construction_complete()` evicts whoever was working the site, frees it, and calls `_materialize_building()` — the exact "instantiate the real scene, apply catalog properties, grant `population_capacity`/`water_wells`/`storage_capacity`, register in `posts`/as a stockpile spot" sequence `_confirm_placement()` used to do synchronously at placement time, now happening once construction finishes instead. Save/load persists in-progress sites separately (`Base._serialize_construction_sites`/`_restore_construction_sites`, its own `"construction_sites"` save section, sharing `_next_placed_id`'s counter/save-id-prefix with `_placed_buildings` since a site's save_id carries over unchanged once it becomes the real building) — `Base._post_by_save_id()` checks both lists, so a citizen saved mid-labor on a site resumes correctly on load.
  - No bespoke art per building here — every `ConstructionSite` reuses the same generic tinted composite (a log + rock + materials-pile, each a cropped region from the pixel-art packs, layered via `ConstructionSite1x1.tscn`/`2x2.tscn`/`2x4.tscn`) regardless of what it'll become; its in-world label is what communicates phase/progress ("Needs: 5 Wood" vs. "Building 42%").
- `Farm` and `LumberCamp` each have their own dedicated scene (`scenes/workstation/Farm.tscn`/`LumberCamp.tscn`) — the old generic `Workstation.tscn` they used to share has since been deleted (dead, unreferenced except in a comment) — but `Base._apply_option_properties()` still copies the catalog's `display_name`/`resource_type`/`output_per_tick` onto each freshly-instantiated node (ghost and real).
- The footprint anchor convention: a building's sprite origin sits at the grid point of its front-most (nearest-camera) cell — `origin + size - Vector2i.ONE` — the exact same point a 1x1 tile/building already anchors to (see `Base._footprint_anchor`/`_footprint_origin`). Deliberately *not* the geometric center of the footprint: for an even-sized footprint that center falls on the grid-line intersection shared by all its cells, which reads as "floating" rather than snapped to a tile. Multi-tile buildings then extend backward (toward smaller gx/gy) from that front cell. `WorldGrid`'s occupancy is seeded at `Base._ready()` from the statically-placed Outpost Hall (the only fixed starting building - a Cabbage Farm and Lumber Camp used to also start built, but the player now builds everything else themselves) via `_reserve_existing_footprint()`, using sizes pulled from `BuildingCatalog.get_option()` rather than hardcoded.
- Isometric grid math is centralized in `IsoUtils` (`scripts/iso_utils.gd`): `grid_to_screen`/`screen_to_grid` with `TILE_WIDTH=128`, `TILE_HEIGHT=64`. Always go through this for grid↔screen conversion rather than re-deriving the diamond-projection math.

**Depth sorting: everything sortable is a direct child of `Base`.** `Base` itself has `y_sort_enabled = true`, and `OutpostHall`/`Aldric`/`Brenna`/`Cass`/dynamically-placed buildings (`add_child` directly on `Base` - includes every Farm/Lumber Camp/etc. now, since only the Outpost Hall starts fixed)/trees (`WorldGrid`'s `trees_container` is `Base` itself) are all *direct* children of it — there are deliberately no intermediate grouping nodes like the old `Workstations`/`Buildings`/`Trees`/`Characters` containers. That grouping was tried and removed: a plain `Node` (non-`CanvasItem`) container does **not** transparently pass its children into the parent's y-sort the way you'd hope — Godot only y-sorts direct `CanvasItem` children, so anything one level deeper renders in plain tree order regardless of position (confirmed by planting a tree on the Outpost Hall's own back tile and watching it render in front of the whole building instead of behind it). If you need editor-organization grouping again, it has to be solved another way (e.g. editor-only groups, not scene-tree parents) — don't reintroduce a Node2D/Node wrapper between `Base` and any sortable entity.
- **`IsoGround` is deliberately *not* part of this y-sort competition — it's pinned behind everything via `z_index = -2` (set on the `IsoGround` node itself, in `scenes/world/IsoGround.tscn`).** It's a single `Node2D` holding every ground tile as a child, so it only has *one* y-sort key (its own `position.y`, ~170) no matter how many tiles it contains. Anything placed toward the "back" of the map (small/negative `gx+gy`, which renders at a smaller screen-Y than 170 — the whole top quadrant of the diamond) would sort *before* that single key and get painted over by the entire ground layer, vanishing behind it. `z_index` sidesteps the problem entirely rather than trying to patch the y-sort math: it's evaluated before y-sort and applies regardless of position, so the ground is unconditionally the backmost layer and every real y-sort participant (buildings/trees/characters, all default `z_index = 0`) sorts normally among itself. Verified by planting a tree at the map's most extreme corner `(-5,-5)` and confirming it renders on top of the ground there.
  - **A third layer sits between the two:** the Farm-family plot sprite (`Farm.tscn`/`CropStation.tscn`'s `Sprite2D`, the flat tilled-soil composite covering the whole 2x2 footprint) is `z_index = -1` — above the ground (so the tilled-soil texture still paints over the grass beneath it) but below every normal y-sort participant (so it can never occlude a character, unlike a real building). The bug this fixed: a farm plot has no actual height (it's flush ground, not a raised structure the way a House/LumberCamp/etc. legitimately is), but at the default `z_index = 0` it still won y-sort ties against a character standing within/behind its drawn footprint (which extends backward from its front-anchor tile, per the footprint anchor convention below) the same way a real building correctly does — reading as "solid ground tile hiding a person standing on open dirt," which it plainly shouldn't. Giving it its own z-layer strictly between ground and everything else fixes this unconditionally, the same reasoning as `IsoGround`'s own `z_index` rather than trying to patch the y-sort key. If another "flush with the ground, must never occlude a character" sprite shows up later (as opposed to a genuinely raised building, which should keep sorting normally), give it `z_index = -1` too rather than inventing a fourth layer.

**UI panels** (`BuildMenu`, `RecruitPanel`, `CropPanel`, `SkillPanel`, all `CanvasLayer`) share the same pattern: build a list of buttons/labels dynamically from options, slide/fade in via a parallel `Tween` on open, reverse-tween + `queue_free` cleanup on close, and (the option-picker ones) support number-key shortcuts (`1`-`9`) in addition to mouse clicks.

**Visuals/juice conventions used throughout** (`Character`, `Workstation`, `HUD`, panels): hover tints via `modulate` tween, "punch" scale tweens on selection/assignment events, and tween-based count-up animations for HUD resource labels. Match these conventions for new interactive nodes rather than introducing new animation idioms. `Workstation` used to also loop a +/-8% scale pulse on its sprite while a worker was active - removed per an explicit request ("remove the working animation from all buildings, the villagers will be the ones animated when working"), since it visibly swept over (and could hide) the worker standing on the post, especially once building sprites grew to cover their whole footprint (see the art-reskin notes in `Outpost_Survival/Actionable Ideas/Implement New Art.md`). No replacement "working" animation exists on `Character`/`CombatUnit` yet - that's implied future work, not done here.

**Art:** hand-drawn `iso_*.svg` sprites were the original art direction but have since been fully replaced by cropped regions from pixel-art packs (`art/Pixel Isometric 16x16/`, `art/Tiny Pixel Art/`, `art/UIBundleFree/`) - an `AtlasTexture` with a `region: Rect2` picked out of a shared pack sheet, the same approach the Rock/RockDecoration scenes and every building use today. Every `iso_*.svg` has been deleted as dead except `iso_selection_ring.svg` (`Character.tscn` still uses it), along with the older non-`iso_`-prefixed top-down set and the now-empty `Workstation.RESOURCE_VISUALS` dict that used to map sprites onto it. When adding a new pack-cropped sprite: verify the region is actually isolated (no bleed from a neighboring sprite in the sheet - a connected-component scan over alpha, or just visually zooming into the crop, catches this) and no other scene already uses that exact region before reusing it.

**Visual style — deliberately AoE2-style dimetric, not true isometric:** the game targets the classic RTS "2:1" look (2 horizontal px per 1 vertical px), not a real 3D isometric camera. The rules below were written for hand-drawn flat-shaded SVG art (not 3D-rendered-then-quantized like AoE2 actually was) and describe the standard any new **hand-authored** asset should still follow - they're largely moot for today's pack-cropped sprites, which inherit whatever projection/lighting the source pack already used:
- **Projection:** tiles are 2:1 diamonds (`IsoUtils.TILE_WIDTH=128`/`TILE_HEIGHT=64`); any sloped edge on a building/wall should keep that same ~2:1 run:rise (e.g. a 45px horizontal run pairs with a ~22px vertical rise), so new assets read as the same camera angle as the ground tiles. It's orthographic — nothing should scale or fade with screen position.
- **Fixed light from the upper-left:** every asset with volume (buildings, workstations, wall corners) gives its left/front-facing plane a lighter fill and its right-facing plane a noticeably darker one (e.g. `iso_outpost_hall.svg`'s `#4f4d40` front wall vs `#302e27` right wall). Ground tiles encode the same rule via a top-left-to-bottom-right `linearGradient`. When an asset has two structurally different faces (like the wall corner pieces), they must differ in shade even if a straight run only shows one visible face and doesn't need the split.
- **Directional drop shadows:** the soft ellipse under an object is offset down-and-right of the object's own anchor point (opposite the upper-left light), never centered under it — offset roughly 8% of the asset's width right and 4-5% of its height down. Flat ground overlays (e.g. the farm plot's tilled-soil tint) aren't cast shadows and stay centered.
- **Chunky, compressed scale:** buildings are stylized and undersized relative to real architecture, sized in whole-tile footprints (`BuildingCatalog`'s `grid_size`) rather than realistic proportions — legibility over accuracy.
- **Footprint silhouette:** every building is a square/rectangle rotated so one corner points straight down at the camera — like the ground tiles and the farm plot, never a flat elevation-view front face. Concretely: a front-ground vertex, two wall faces (left/right) rising from it as parallelograms sloped at the same 2:1 grid angle to reach the footprint's left/right corners, then the roof above. `iso_outpost_hall.svg`/`iso_house.svg` are the reference implementation for a 2x2 footprint.
- **Footprint proportions must stay exactly 2:1** — an NxN footprint's flat diamond is `(N*128)` wide by `(N*64)` tall, full stop. Don't add a decorative margin/inset by shaving a fixed pixel amount off each side: insetting the same number of pixels off a 2:1 shape's width and height changes the *ratio* (a real bug in `iso_workstation_farm.svg`'s first 2x2 pass — an 8px-per-1x1-tile inset scaled naively to 2x2 left it 224x96, a 2.33:1 rectangle, visibly squashed next to the true 2:1 ground tiles). If a margin is wanted, add it as canvas padding *around* the true-proportioned diamond, or inset both axes by the same fraction of their own half-width/half-height — never the same fixed pixel count on both axes.
