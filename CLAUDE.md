# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Godot 4.7 (GDScript) base-building/survival game ("outpost survival"), inspired by State of Decay 2, Warcraft 3, Age of Empires 2, Project Zomboid, RuneScape, and Battle Brothers — grimdark medieval fantasy setting. Design notes live in `Outpost Survival Game Ideas`. The project is early-stage: a single base scene with recruitable characters who can be assigned to gathering workstations.

Renderer is `gl_compatibility` (both desktop and mobile). Main scene: `res://scenes/base/Base.tscn`.

## Running / building

This is a Godot editor project, not a CLI-buildable one. Open and run it with the Godot 4.7 editor (or `godot4 --path .` / `godot4 -e --path .` if the Godot binary is on PATH). There are no automated tests, lint configs, or CI in this repo — verify changes by running the project in the editor and exercising the affected flow.

## Architecture

**Autoload singletons:**
- `GameState` (`autoload/game_state.gd`) holds the global resource pool (`food`, `wood`) as a plain dictionary, exposes `add_resource`, `can_afford`, `spend`, and emits `resources_changed` for UI to listen to. `add_resource` clamps every resource at a minimum of 0 — this is what makes the food drain below safe to run unconditionally rather than gating it on affordability. Also tracks `population_count`/`population_capacity` (`add_population_capacity`, `population_changed`), and runs its own food-consumption `Timer` (created in code in `_ready()` — autoloads have no `.tscn`, so there's nowhere to put a scene Timer node): every `CONSUMPTION_INTERVAL` (1s) it drains `FOOD_PER_CITIZEN * population_count` food, regardless of whether citizens are assigned to a post. This is the only per-citizen cost currently modeled — there's no starvation penalty yet if food hits 0, it just stops going lower.
- `WorldGrid` (`autoload/world_grid.gd`) is the single source of truth for grid-cell occupancy and the tree registry, so buildings (via `Base`) and trees (via lumberjack replanting) can never overlap each other. `Base._ready()` calls `WorldGrid.configure(ground_origin, bounds_min, bounds_max, container)` once at startup. Exposes `grid_to_local`/`local_to_grid` (thin wrappers over `IsoUtils` plus the ground's screen offset), `is_in_bounds`/`is_free`/`reserve`/`release` (single-cell occupancy), and `plant_tree`/`find_available_tree`/`find_plantable_cell` (the tree registry). Anything that needs grid↔screen conversion or occupancy checks — `Base`'s building placement, `Character`'s lumberjack AI — goes through this rather than each maintaining separate state.

**Camera (`scripts/rts_camera.gd`, `RtsCamera` class, `Base`'s `Camera2D` child):** scroll wheel zooms (`MOUSE_BUTTON_WHEEL_UP`/`DOWN`, tweened, clamped to `zoom_min`/`zoom_max`), middle-mouse hold+drag pans 1:1 with the cursor, and the cursor sitting within `edge_scroll_margin` px of the viewport edge pans continuously every `_process`. All three consume the event in `_input()` (not `_unhandled_input()`) so they never reach `Base`'s "any mouse button click deselects/closes panels" checks — `_input` always runs before `_unhandled_input` regardless of node tree order, which is what makes that interception reliable. `Base._ready()` calls `camera.configure_limits(min_local, max_local)` using the same ground-bounds corners it feeds `WorldGrid.configure`, so panning/edge-scroll stop at the map edge (plus `limit_margin`). **`Camera2D.limit_left/top/right/bottom` only clamp the rendered view, not the `position` property itself** — code that sets `position` directly (the drag/edge-scroll handlers here) can drift `position` arbitrarily far past the limits with zero visible change, then the camera appears to "lag" for exactly that same distance before the opposite direction has any visible effect. `_clamp_position()` clamps `position` to `limit_left/right/top/bottom` manually after every drag-motion and edge-scroll update — don't add a new way of moving `position` without also calling it, or this regresses. **Non-obvious gotcha verified empirically in this Godot build:** `Camera2D.zoom` values *greater* than 1 magnify (zoom in) and values *less* than 1 zoom out — the opposite of what a literal reading of the Godot docs suggests — so the screen↔world conversions here divide by `zoom` (`screen_delta / zoom`), not multiply. If this ever looks backwards after a Godot upgrade, re-verify that assumption with an actual on-screen test before changing the math blind. The camera's initial `position` is set to `get_viewport_rect().size / 2.0` in `_ready()` specifically to reproduce the exact framing the game had before any camera existed (world origin at the viewport's top-left) — don't hardcode a fixed starting position, it needs to adapt to viewport size.

**Base scene (`scripts/base.gd`, `Base` class) is the top-level coordinator.** It owns the list of `characters` and `posts` (workstations/wall segments), and wires together `TaskPanel` and the click/drag-based selection flow:
- `Character` doesn't distinguish a click from a drag itself — every left-press emits `drag_started(self)` and `Base._on_character_drag_started()` starts tracking it. `Base._handle_drag_input()` resolves it on release: if the cursor never moved more than `DRAG_THRESHOLD` px, it's a plain click (`_on_character_selected()`, opening `TaskPanel` with the list of assignable posts); if it did move, `Base._post_at(mouse_pos)` physics-queries for a `posts` member under the cursor (`PhysicsPointQueryParameters2D`/`intersect_point`, filtered to `result["collider"] in posts` so it ignores other characters/trees/decorative buildings) and either `character.assign_to(post)`s a valid drop or `character.cancel_drag()`s back to its current spot — right-click/`ui_cancel` also cancels mid-drag. `Character.cancel_drag()` deliberately does *not* go through `assign_to()` (which would restart `_stop_lumberjack()`/`_start_lumberjack()` and replay sounds) — an accidental drag-and-miss shouldn't interrupt work in progress.
- Selecting a task from `TaskPanel` assigns the character via `Character.assign_to(post)`; selecting "Idle" unassigns.
- Clicking elsewhere (or `ui_cancel`) deselects and closes the panel.

**Character/post interaction pattern:** `Character` (`scripts/character.gd`) is an `Area2D` with a `CharacterData` resource (name + `gathering` stat, stored as `.tres` files under `resources/characters/`). `assign_to(post)` calls `post.add_worker()`/`remove_worker()` and moves the character to `post.get_worker_spot()`. If the post `is Workstation` (and not a `LumberCamp`, which uses the async loop below instead), a per-character `TickTimer` starts; on timeout, `_on_tick_timer_timeout()` special-cases `Farm` (see below) and otherwise calls `GameState.add_resource(post.resource_type, post.output_per_tick * data.gathering)`. Posts are duck-typed (`Workstation` and `WallSegment` both expose `add_worker`/`remove_worker`/`get_worker_spot`/`display_name` but don't share a base class) — when adding a new assignable post type, match this interface rather than introducing a formal base class.

**Farm (`scripts/farm.gd`) `extends Workstation`, adding `wood_per_tick`.** Unlike a plain `Workstation` tick, a `Farm`'s tick in `Character._on_tick_timer_timeout()` first checks `GameState.can_afford({"wood": wood_per_tick * data.gathering})` — if wood's short, the farm simply produces nothing that tick (no error, no stuck state) — otherwise it spends that wood and adds `output_per_tick * data.gathering` food. Both the food gain and the wood cost scale by the same `data.gathering` multiplier, so a more skilled farmer produces (and consumes) proportionally more, but the wood:food *ratio* stays fixed regardless of who's assigned. This is the game's only production chain so far: Lumber Camp wood feeds Farm food feeds population — running a Farm with no Lumber Camp output eventually stalls it once wood runs out.

**Lumber Camp gathering (tree-based, not the passive per-tick gather Farm still uses):** `LumberCamp` (`scripts/lumber_camp.gd`) `extends Workstation`, adding `search_radius`/`max_cultivated_trees`/`replant_per_harvest`/`wood_per_chop`/`chop_interval` exports — it's still duck-type-compatible as a `post`. The actual walk/chop/replant behavior is a per-character state machine in `Character._run_lumberjack_loop()` (an `await`-based coroutine kicked off by `assign_to` when `post is LumberCamp`, cancelled by bumping `_lumberjack_session` so a stale coroutine notices and returns next time it resumes): find the nearest unclaimed mature `WorldTree` within `search_radius` via `WorldGrid.find_available_tree` → walk to it → chop every `chop_interval` (`WorldTree.harvest()`) until depleted → replant `replant_per_harvest` saplings (via `WorldGrid.find_plantable_cell`/`plant_tree`) capped at `max_cultivated_trees` *per worker* (tracked in `Character._cultivated_trees`, not on the camp — multiple workers can be assigned to one camp) → repeat. `WorldTree` (`scripts/tree.gd`) starts as a small sapling (`is_mature = false`) and tweens its sprite scale up to full size over `grow_time` seconds before it's harvestable; `harvest()` shrinks/fades it out and emits `depleted` once its wood is gone, which `WorldGrid` listens for to free the cell and drop it from the registry. The class is named `WorldTree`, not `Tree` — `Tree` collides with Godot's built-in `Tree` UI control and silently fails to register as a global class if reused.

**Building/placement system:** `BuildingCatalog` (`scripts/building_catalog.gd`) is a static, `RefCounted` catalog of buildable options (id, display name, scene, cost, and — for anything placeable — a `grid_size: Vector2i` footprint). `BuildingCatalog.placeable_options()` filters to entries with `grid_size` (currently Outpost Hall, Farm, Lumber Camp, House — all 2x2 except Lumber Camp, which is 1x1); `get_option(id)` looks one up by id. The HUD's "Build" button opens `BuildMenu` with those options; picking one hands the option `Dictionary` to `Base`, which drives the whole placement flow:
- A translucent "ghost" instance of the option's scene follows the mouse, snapped to the grid, tinted green/red based on `Base._ghost_valid` (in ground bounds, free per `WorldGrid`, and `GameState.can_afford`).
- Left-click confirms (spends resources, reserves the footprint's cells, grants `population_capacity` if the option has one, registers the new node in `posts` if it exposes `add_worker`); right-click/`ui_cancel` cancels.
- `Farm` and `LumberCamp` each have their own dedicated scene (`scenes/workstation/Farm.tscn`/`LumberCamp.tscn`) rather than sharing the old generic `Workstation.tscn` (now unused/dead) — but `Base._apply_option_properties()` still copies the catalog's `display_name`/`resource_type`/`output_per_tick` onto each freshly-instantiated node (ghost and real), since both classes still read `resource_type` at `_ready()` to pick their sprite via `Workstation.RESOURCE_VISUALS`.
- The footprint anchor convention: a building's sprite origin sits at the grid point of its front-most (nearest-camera) cell — `origin + size - Vector2i.ONE` — the exact same point a 1x1 tile/building already anchors to (see `Base._footprint_anchor`/`_footprint_origin`). Deliberately *not* the geometric center of the footprint: for an even-sized footprint that center falls on the grid-line intersection shared by all its cells, which reads as "floating" rather than snapped to a tile. Multi-tile buildings then extend backward (toward smaller gx/gy) from that front cell. `WorldGrid`'s occupancy is seeded at `Base._ready()` from the statically-placed Outpost Hall/Farm/Woodpile via `_reserve_existing_footprint()`, using sizes pulled from `BuildingCatalog.get_option()` rather than hardcoded.
- `PerimeterWall` (`scripts/perimeter_wall.gd`) is unrelated leftover code from an earlier wall-building concept: it depends on a `BuildSlot` scene (`res://scenes/build_slot/BuildSlot.tscn`) that no longer exists, so **`PerimeterWall.tscn` will fail to parse if instantiated.** It isn't referenced by `Base.tscn`, so this doesn't affect the game as shipped — don't wire it in without rebuilding the build-slot concept from scratch.
- Isometric grid math is centralized in `IsoUtils` (`scripts/iso_utils.gd`): `grid_to_screen`/`screen_to_grid` with `TILE_WIDTH=128`, `TILE_HEIGHT=64`. Always go through this for grid↔screen conversion rather than re-deriving the diamond-projection math.

**Depth sorting: everything sortable is a direct child of `Base`.** `Base` itself has `y_sort_enabled = true`, and `OutpostHall`/`Farm`/`Woodpile`/`Aldric`/`Brenna`/`Cass`/dynamically-placed buildings (`add_child` directly on `Base`)/trees (`WorldGrid`'s `trees_container` is `Base` itself) are all *direct* children of it — there are deliberately no intermediate grouping nodes like the old `Workstations`/`Buildings`/`Trees`/`Characters` containers. That grouping was tried and removed: a plain `Node` (non-`CanvasItem`) container does **not** transparently pass its children into the parent's y-sort the way you'd hope — Godot only y-sorts direct `CanvasItem` children, so anything one level deeper renders in plain tree order regardless of position (confirmed by planting a tree on the Outpost Hall's own back tile and watching it render in front of the whole building instead of behind it). If you need editor-organization grouping again, it has to be solved another way (e.g. editor-only groups, not scene-tree parents) — don't reintroduce a Node2D/Node wrapper between `Base` and any sortable entity.
- **`IsoGround` is deliberately *not* part of this y-sort competition — it's pinned behind everything via `z_index = -1` (set on the `IsoGround` node itself, in `scenes/world/IsoGround.tscn`).** It's a single `Node2D` holding every ground tile as a child, so it only has *one* y-sort key (its own `position.y`, ~170) no matter how many tiles it contains. Anything placed toward the "back" of the map (small/negative `gx+gy`, which renders at a smaller screen-Y than 170 — the whole top quadrant of the diamond) would sort *before* that single key and get painted over by the entire ground layer, vanishing behind it. `z_index` sidesteps the problem entirely rather than trying to patch the y-sort math: it's evaluated before y-sort and applies regardless of position, so the ground is unconditionally the backmost layer and every real y-sort participant (buildings/trees/characters, all default `z_index = 0`) sorts normally among itself. Verified by planting a tree at the map's most extreme corner `(-5,-5)` and confirming it renders on top of the ground there. If another "must always render behind/in front regardless of y-sort" layer shows up later, reach for `z_index` again rather than fighting the y-sort key.

**UI panels** (`TaskPanel`, `BuildMenu`, both `CanvasLayer`) share the same pattern: build a list of buttons dynamically from options, slide/fade in via a parallel `Tween` on open, reverse-tween + `queue_free` cleanup on close, and support number-key shortcuts (`1`-`9`, plus `0` for idle in `TaskPanel`) in addition to mouse clicks.

**Visuals/juice conventions used throughout** (`Character`, `Workstation`, `WallSegment`, `HUD`, panels): hover tints via `modulate` tween, "punch" scale tweens on selection/assignment events, looping pulse tweens on active workstations, and tween-based count-up animations for HUD resource labels. Match these conventions for new interactive nodes rather than introducing new animation idioms.

**Art:** isometric sprites (`iso_*.svg`) are the current set in active use; the non-`iso_`-prefixed sprites (`workstation_farm.svg`, `outpost_hall.svg`, etc.) are an older top-down set, unreferenced by any scene or script — dead, kept only as history. `Workstation.RESOURCE_VISUALS` maps `resource_type` → texture/centering/offset for iso sprites.

**Visual style — deliberately AoE2-style dimetric, not true isometric:** the game targets the classic RTS "2:1" look (2 horizontal px per 1 vertical px), not a real 3D isometric camera. Since art is hand-drawn flat-shaded SVG (not 3D-rendered-then-quantized like AoE2 actually was), these rules exist to fake that look by hand — follow them for any new `iso_*.svg` asset:
- **Projection:** tiles are 2:1 diamonds (`IsoUtils.TILE_WIDTH=128`/`TILE_HEIGHT=64`); any sloped edge on a building/wall should keep that same ~2:1 run:rise (e.g. a 45px horizontal run pairs with a ~22px vertical rise), so new assets read as the same camera angle as the ground tiles. It's orthographic — nothing should scale or fade with screen position.
- **Fixed light from the upper-left:** every asset with volume (buildings, workstations, wall corners) gives its left/front-facing plane a lighter fill and its right-facing plane a noticeably darker one (e.g. `iso_outpost_hall.svg`'s `#4f4d40` front wall vs `#302e27` right wall). Ground tiles encode the same rule via a top-left-to-bottom-right `linearGradient`. When an asset has two structurally different faces (like the wall corner pieces), they must differ in shade even if a straight run only shows one visible face and doesn't need the split.
- **Directional drop shadows:** the soft ellipse under an object is offset down-and-right of the object's own anchor point (opposite the upper-left light), never centered under it — offset roughly 8% of the asset's width right and 4-5% of its height down. Flat ground overlays (e.g. the farm plot's tilled-soil tint) aren't cast shadows and stay centered.
- **Chunky, compressed scale:** buildings are stylized and undersized relative to real architecture, sized in whole-tile footprints (`BuildingCatalog`'s `grid_size`) rather than realistic proportions — legibility over accuracy.
- **Footprint silhouette:** every building is a square/rectangle rotated so one corner points straight down at the camera — like the ground tiles and the farm plot, never a flat elevation-view front face. Concretely: a front-ground vertex, two wall faces (left/right) rising from it as parallelograms sloped at the same 2:1 grid angle to reach the footprint's left/right corners, then the roof above. `iso_outpost_hall.svg`/`iso_house.svg` are the reference implementation for a 2x2 footprint.
- **Footprint proportions must stay exactly 2:1** — an NxN footprint's flat diamond is `(N*128)` wide by `(N*64)` tall, full stop. Don't add a decorative margin/inset by shaving a fixed pixel amount off each side: insetting the same number of pixels off a 2:1 shape's width and height changes the *ratio* (a real bug in `iso_workstation_farm.svg`'s first 2x2 pass — an 8px-per-1x1-tile inset scaled naively to 2x2 left it 224x96, a 2.33:1 rectangle, visibly squashed next to the true 2:1 ground tiles). If a margin is wanted, add it as canvas padding *around* the true-proportioned diamond, or inset both axes by the same fraction of their own half-width/half-height — never the same fixed pixel count on both axes.
