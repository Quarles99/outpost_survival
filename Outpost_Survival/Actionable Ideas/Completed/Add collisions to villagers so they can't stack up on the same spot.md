## Completion write-up (2026-07-20)

Note was empty when picked up - title alone was clear enough scope: citizens visibly walking through/on top of each other with no separation.

**Root cause:** `Character._move_to()` already routes through a `NavigationAgent2D` (added in an earlier session for static obstacle routing - see its own doc comment), but `avoidance_enabled` was explicitly left `false` - "citizens don't dodge each other, only the map's fixed obstacles, per an explicit scoping decision to keep this port simpler than the battle sandbox's." `CombatUnit` already has working agent-vs-agent RVO avoidance in the exact same engine feature; this pass just turns the same thing on for `Character` and wires it the same way.

**What changed (`scripts/character.gd`):**
- `_ready()` now sets `nav_agent.radius = AVOIDANCE_RADIUS` (18.0), `nav_agent.avoidance_enabled = true`, `neighbor_distance`/`time_horizon_agents` tuned down from the NavigationServer's crowd-sim defaults (500px/~20s, meant for large crowds reacting to far-off traffic) to 150px/1.5s - a settlement's population is a small handful of agents, same reasoning `CombatUnit` already tuned its own down for a ~12-unit battle. `AVOIDANCE_RADIUS` is deliberately well under `CollisionShape2D`'s own 36px click-hitbox radius - that's sized generously for easy clicking, not "how close two citizens can stand."
- `_move_to()`'s per-frame loop no longer applies `direction * move_speed * delta` to `_base_position` directly - it calls `nav_agent.set_velocity(direction * move_speed)` instead, and the actual position update moved into a new `_on_velocity_computed(safe_velocity)` handler (connected once in `_ready()`), fired asynchronously once avoidance has computed a collision-adjusted velocity. Exactly the same split `CombatUnit._on_velocity_computed` already uses, including tracking a `_move_delta` instance var so the handler applies the right delta even though it may not fire on the exact frame `set_velocity()` was called.

**Known gap, not addressed by this pass:** avoidance only applies while a citizen is actually inside `_move_to`'s loop - once arrived and stopped, nothing keeps pushing them apart. Several citizens stationed at the very same shared `WorkSpot` marker (e.g. multiple builders on one construction site, see the "Allow multiple builders" completion write-up's own note on this) can still visually stack once all arrived. Fixing that would mean giving stationary workers on a shared spot their own small offset, a separate, additive change from "don't walk through each other."

**Verification:** `flatpak run org.godotengine.Godot --headless --path . --quit` clean. Verified the actual avoidance effect with a throwaway headless script (`--headless --script res://verify_avoidance_test.gd`, deleted after): instantiated real `Base.tscn`, commanded two of the three starting citizens (`_move_to()` called directly) toward the exact same target point from different starting positions, ran ~4 seconds of frames, and confirmed they ended up **103px apart** rather than converging to the same point (which is what happened before this change, and what still happens for e.g. two builders converging on one WorkSpot). Also live-verified via a real running window that ordinary gameplay (hauling, assignment) still works with no new runtime errors, and separately confirmed (screenshot) that a fresh boot's default camera view - which is what actually prompted the "trees disappeared" investigation, see [[Increase max zoom out level]]'s own follow-up - shows the Outpost Hall with all 3 starting citizens clearly visible and distinct, not overlapping.

**Docs updated:** `Docs/mechanics.md`'s Pathfinding section no longer says citizens don't dodge each other - updated to describe the new RVO behavior and the shared-WorkSpot caveat above. `Game Systems/Balance.md`'s Movement & Work Pace table gained two new rows for the avoidance radius/neighbor-distance/time-horizon constants.
