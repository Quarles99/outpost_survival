## Completion write-up (2026-07-20)

Note was empty when picked up - scope confirmed with the user: +/- stepper buttons on the existing click-to-open building panels (BuildingInfoPanel/CropPanel/TrainingGroundPanel), letting the player cap a post's worker count anywhere from 0 up to its `max_workers`, independent of the existing right-click disable toggle.

**`Workstation.desired_workers`** (`scripts/workstation.gd`): new `@export var desired_workers: int = -1` - a softer, steppable version of `disabled` (which is all-or-nothing). -1 is a sentinel meaning "not yet set"; `_ready()` normalizes it to `max_workers` the instant the node enters the tree, so every existing catalog entry/save that's never heard of this field behaves exactly as before (full capacity, today's implicit default). Two new methods: `get_effective_worker_cap()` (0 if `disabled`, else `clampi(desired_workers, 0, max_workers)` - `disabled` still wins outright regardless of this value, same as always) and `set_desired_workers(value)` (clamps, no-ops if unchanged, emits the new `desired_workers_changed` signal otherwise).

**`Base._run_job_assignment()`**: both places that used to read `post.max_workers` directly (the shared per-skill capacity sum, and the pool-to-post distribution loop) now call `post.get_effective_worker_cap()` instead - this single change is what actually makes the setting take effect, since every other job-post mechanic in the game already funnels through this one Gale-Shapley pass.

**Eviction on reduction**: new `_wire_workstation_desired_workers`/`_on_desired_workers_changed`, wired at every place a building is created (`_materialize_building`, the save/load restore loop, `_spawn_construction_site`) alongside the existing `_wire_workstation_disable`. Mirrors `_on_post_disabled_changed`'s shape: evict just enough of this specific post's currently-assigned citizens to fit the new (lower) cap, then re-run `_run_job_assignment()` so the freed citizen(s) get a chance to land somewhere else immediately rather than sitting idle until some other trigger reruns assignment.

**UI**: identical "Workers: N/max" row with a `-`/`+` `Button` on either side added to all three panels (`BuildingInfoPanel.tscn`/`CropPanel.tscn`/`TrainingGroundPanel.tscn`), each wired the same way - `open_for()` gained `worker_count`/`worker_max`/`on_worker_delta` params, the callback is `func(delta): building.set_desired_workers(building.desired_workers + delta)` bound by Base at the same three call sites that already open these panels (`_on_building_info_clicked`/`_on_farm_clicked`/`_on_training_ground_clicked`). BuildingInfoPanel reuses its existing `show_employees` flag to hide the row for House (never a job post, no desired_workers concept) rather than adding a redundant bool.

**Save/load**: `desired_workers` only written to a placed-building's save entry when it's actually been lowered below `max_workers` (`_serialize_placed_buildings`), same conditional-field convention `disabled`/`upgraded`/etc. already use - an old save with no such field just gets the normal `_ready()`-time normalization to full capacity on restore, so this is fully backward compatible.

**Overflow bug found and fixed along the way**: adding the new row pushed all three panels' content past their old hardcoded pixel heights - same class of bug as the HUD overflow found while doing [[Make the resource display consistent across all resources]] (screenshot showed an employee row clipped off the bottom of the screen entirely). Fixed the same way: converted each panel's root `Control` to a `PanelContainer` (`theme_type_variation = &"DialogPanel"`, reusing the existing texture style without touching the shared resource) wrapping a `MarginContainer` (10px padding, replacing the old VBoxContainer's own offset-based padding) around the content `VBoxContainer`, so each panel now auto-sizes to its actual content. These three are anchored bottom-left (grow-upward), unlike HUD's top-right (grow-downward) box - Godot's Container auto-sizing only grows in the positive/away-from-anchor direction from whichever offset is left set, so rather than fight that, switched all three to anchor from the top-left instead with a fixed `offset_top` computed to match each panel's old starting Y position (e.g. BuildingInfoPanel's old bottom-anchored `offset_top=-220` on a 720px-tall viewport put its top edge at 500, so the new top-anchored version sets `offset_top=500` directly) - visually opens in the same place, but now grows downward instead of clipping.
