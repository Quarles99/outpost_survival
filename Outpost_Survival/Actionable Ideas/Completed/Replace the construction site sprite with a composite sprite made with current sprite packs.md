## Completion write-up (2026-07-20)

**Asset survey, confirmed with the user before implementing:** searched every isometric-style pack currently in use (`Pixel Isometric 16x16`, `Tiny Pixel Art`) for the specific named props - no literal bench/hammer/saw sprite exists in either. Found and used instead: a wood log stump (`Tiny Pixel Art/Isometric_MedievalFantasy_Tiles.png`, two color variants), a rock rubble pile and a round boulder (same sheet), and a goods/materials pile (`Pixel Isometric 16x16/Structures2.png` - the exact crop `Rect2(98,43,28,20)` StorageFacility already ships with, reused here as "a pile of delivered materials" rather than hand-drawing a new SVG or reaching into the flat RPG-icon sheet (`art/items_sheet.png`) that would've clashed with the isometric world style).

**Three footprint-shape-specific scenes**, not one generic scaffold stretched to fit (`scenes/workstation/ConstructionSite{1x1,2x2,2x4}.tscn` - the three distinct `grid_size` values every current `BuildingCatalog` entry actually uses): each scatters 3-6 of the props above across its own footprint, using the same real building's collision box (LumberCamp's for 1x1, OutpostHall's for 2x2, StorageFacility's for 2x4) so the site's clickable area already matches what it'll become. `Base.CONSTRUCTION_SITE_SCENES` (a `Vector2i -> PackedScene` dict) replaces the old single `CONSTRUCTION_SITE_SCENE` constant; `_spawn_construction_site` picks the right one via the new `_construction_site_scene_for(size)`, falling back to 1x1 for any future footprint shape without its own composite (none exist today). Deleted the old generic `ConstructionSite.tscn`/`iso_workstation_generic.svg`-based scene entirely - fully superseded, zero remaining references.

**Two real bugs found and fixed along the way, both from the same root cause** (`ConstructionSite` extends `Workstation`, which hard-requires a child literally named `$Sprite2D` for its own texture/tint bookkeeping) - the new scattered-prop scenes don't have a single canonical sprite the way every other building does:
- Runtime crash-adjacent error on every single site spawn (`ERROR: Node not found: "Sprite2D"` / `Invalid access to property 'texture' on a base object of type 'null instance'`) - never caught by the headless `--quit` compile check used throughout this session, since that never actually instantiates a `ConstructionSite` (only real gameplay does). Fixed by renaming one prop per scene to literally `Sprite2D` (the crate/pile prop) so `Workstation._ready()` resolves correctly, `_default_texture` correctly falls back to that prop's own baked texture (no `RESOURCE_VISUALS` entry for `"construction"`), same pattern already established.
- `Workstation.refresh_visual()`/`_ready()` only apply `sprite_tint`/`XRAY_MATERIAL` to that single canonical sprite - overrode both in `construction_site.gd` to walk every `Sprite2D` child instead (same "walk every Sprite2D child" pattern `StorageFacility.gd` already uses for its own Pile1-4, since it doesn't extend `Workstation` and never had this constraint), so every scattered prop tints together and x-ray-reveals consistently with every other occluder class.

**A third, much harder bug, isolated but not from a code defect:** one specific `AtlasTexture` crop (the wrong goods-pile Y-coordinate, `Rect2(98,75,...)` - a row I'd misread from a low-resolution 10x-scaled preview as "a plain wooden crate" when it's actually just a darker-colored variant of the same red goods-pile creature-bundle shape) rendered correctly in every offline `magick`-cropped preview but as a garbled reddish blob in the actual running game, consistently, across multiple placements. Spent significant time ruling out: crop-coordinate math (re-verified three times), the shared X-ray shader material (isolated by testing with/without it), stale `.godot/imported/` texture cache (force-reimported both source PNGs via `--headless --editor --quit`, no change), and node/scene structure (isolated a bare `Node2D` scene instancing just the composite in question, no `Base`/camera/y-sort involvement, still wrong). Only fully isolating and enlarging the *exact* crop at high zoom (not eyeballing a small multi-row preview) revealed it wasn't a "clean crate" at all - it was legitimately that same reddish creature-pile shape, just a step further down the sheet. Standardized all three scenes on the one crop already proven correct in shipping code (`Rect2(98,43,28,20)`, StorageFacility's own) rather than continuing to hunt for a literal crate elsewhere in the sheet, per the user's earlier "use what's available" call.

**Verification:** `flatpak run org.godotengine.Godot --headless --path . --quit` clean throughout. Live-verified via a temporary isolated diagnostic scene (`scenes/_diag_test.tscn`, deleted after) directly instancing all three `ConstructionSite*.tscn` side by side with a fixed camera - confirmed all three render their full prop set correctly with zero runtime errors, avoiding the camera-panning/click-precision flakiness that made in-game `xdotool`-driven placement unreliable earlier in this session. Also confirmed once via a real in-game Lumber Camp placement (before the pile-coordinate bug was found) that the 1x1 site's log/rock props, collision box, and "Needs: N Wood" label all work correctly end-to-end through the real build-menu -> hauling -> labor -> completion flow.
