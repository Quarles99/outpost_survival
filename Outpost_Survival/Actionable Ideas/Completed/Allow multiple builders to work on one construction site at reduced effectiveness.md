## Completion write-up (2026-07-20)

**What changed:** `ConstructionSite` (`scripts/construction_site.gd`) previously inherited `Workstation.max_workers`' default of 1 - a site could only ever have one builder, regardless of how many construction-skilled citizens were idle/hauling with nothing better to do. Now overrides it to `MAX_BUILDERS := 3` in `_ready()` (set before `super._ready()`), the exact same pattern `TrainingGround.get_unit_cap()`/`_ready()` already uses to override its own capacity - no changes needed anywhere in `Base._run_job_assignment`'s Gale-Shapley pooling, since it already reads `post.max_workers` generically rather than assuming 1.

**Reduced effectiveness:** `Character._run_construction_loop` now scales each worker's own per-tick labor gain by `1 / active_workers^CONSTRUCTION_MULTI_BUILDER_EXPONENT` (new constant, `0.5` - a square-root diminishing-returns curve), read fresh at the moment each tick resolves so it responds immediately as workers join or leave mid-build. A single worker is unaffected (factor = 1.0); 2 workers finish a site ≈1.41x as fast as one alone (not 2x), 3 workers ≈1.73x (not 3x) - more builders always help, but crowding onto one site has a real, escalating cost rather than being either useless or a free linear multiplier. Flagged as a first-pass curve, not tuned via playtesting, matching this codebase's existing convention for freshly-introduced tunable mechanics (see `CONSTRUCTION_LABOR_PER_TICK`'s own doc comment) - a flatter or steeper exponent is a one-line change if 3-builder sites end up feeling too strong or too weak once played.

**Not changed:** worker positioning - all builders on a site still converge on the same single `WorkSpot` marker and visually stack, same as `TrainingGroundPanel`'s existing 3+-unit training buildings already do (confirmed by inspecting `TrainingGround.tscn` - it has exactly one `WorkSpot` too, despite `BASE_UNIT_CAP = 3`). Not a new problem introduced here, and not addressed by this pass.

**Docs updated:** `Docs/mechanics.md`'s Construction section now mentions a site can take several builders at once, at reduced effectiveness per worker. `Docs/stats.md`'s Construction table got a new "Max workers per site" row (3, with the effectiveness formula) and, while I was directly in that table, two unrelated stale numbers in the same rows were corrected to match actual current code: Labor required's formula (was showing the pre-2026-07-20-balance-pass constants `2.0`/`10.0`, actual current `0.5`/`2.0` - see the Balance sheet completion write-up above) and Labor added per work cycle (was showing a stale `1.2`, actual current `2.0`).

**Verification:** `flatpak run org.godotengine.Godot --headless --path . --quit` (full project load, registers autoloads) completed with zero compile errors after the `construction_site.gd`/`character.gd` changes. Not verified with a live playthrough - the user had their own Godot session open and playtesting at the time (see the same note on the two completion write-ups above).
