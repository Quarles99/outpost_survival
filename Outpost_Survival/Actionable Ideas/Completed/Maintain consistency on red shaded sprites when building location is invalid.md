## Completion write-up (2026-07-20)

**Root cause:** `Workstation.refresh_visual()` (`scripts/workstation.gd:191`) sets `sprite.modulate = sprite_tint * (DISABLED_TINT if disabled else Color.WHITE)` on the child `Sprite2D`. Separately, `Base._update_ghost()` (`scripts/base.gd`) sets `VALID_TINT`/`INVALID_TINT` (green/red) on the ghost's *root* node. Godot's `CanvasItem.modulate` compounds multiplicatively down the tree, so the final rendered color was `INVALID_TINT * sprite_tint`. Untinted posts (Lumber Camp, Stone Mine, Well - no `sprite_tint` export or default `Color.WHITE`) rendered a clean red. Every post that uses `sprite_tint` to distinguish itself on a shared sprite (Farm-family crops, Workshop's Mill/Bakery/Brewery, TrainingGround's Barracks/Archery/Mage Tower) rendered a muddied, inconsistent shade instead - e.g. Fruit Orchard's dark tint `(0.55, 0.22, 0.2)` times invalid-red multiplied down to a near-black brown, barely readable as "invalid" next to Lumber Camp's clean red.

**Fix:** `Base._on_build_option_selected()` now resets the ghost's `sprite_tint` to `Color.WHITE` immediately after `_apply_option_properties()` (which sets the real tint) and before `add_child()` triggers `_ready()`/`refresh_visual()` - gated on `_ghost.has_method("refresh_visual")` so only Workstation subclasses are touched, duck-typed like the rest of the placement code. Every ghost's sprite now starts neutral, so the root's `VALID_TINT`/`INVALID_TINT` is the only color applied while placing, matching what untinted buildings already looked like. The eventual placed building is a separate instance built fresh by `_materialize_building()`/`_confirm_placement()` (its own `_apply_option_properties()` call with the real `option["sprite_tint"]`), so the real per-building color is unaffected - only the ghost preview loses its tint distinction while being dragged.

**Verification:** Traced the exact multiply through code (confirmed `sprite_tint` defaults - Cabbage `(0.5,0.75,0.4)`, Grain `(0.85,0.75,0.35)`, Fruit `(0.55,0.22,0.2)`, etc. in `building_catalog.gd` - against `VALID_TINT`/`INVALID_TINT` in `base.gd`) and confirmed ordering (`_apply_option_properties` runs before `add_child`, so the override lands before `_ready()`/`refresh_visual()` reads `sprite_tint`). Not verified with an in-editor screenshot this pass - the user had a live Godot session/playtest running at the time, so no competing instance was launched. Worth a quick live check next time the build menu is open: any tinted post's ghost should now match Lumber Camp's red/green exactly.

**Known gap:** while placing, a Cabbage Farm ghost and a Grain Farm ghost now look visually identical (both neutral, tinted only by validity) - the crop-specific color is only visible once actually placed. This trades ghost-preview crop identification for placement-feedback consistency; flag if the identification loss ends up mattering in practice.
