**Not done / deferred - villager + marauder animated sprites:** the two composed sheets (`art/Spell of Mastery Pack/som-sprite-sheet.png` = villager, `som-sprite-sheet(6).png` = marauder) are a from-scratch animation system, not an asset swap - `Character` and `CombatUnit` currently render a single static `Sprite2D` with no facing/direction state at all. Findings for whoever picks this up:

Rows 0-2 = south-facing (idl1/aware/fall/lay/idl2, then mv1-4/idl3, then atk1-3/point/idl4), rows 3-5 = the same for north-facing, **except** north's `fall`/`lay` cells (row 3, col 2-3) are blank in the exported sheet - the death animation deliberately reuses south row 0's `fall`/`lay` cells for both facings (see the composer's `makeAnimTable()` in `Outpost_Survival/spell-of-mastery-sprite-composer.html` around line 420).

## Follow-up (2026-07-17) - House/Tree unified to a 4x scale

House and Tree (the only two scenes using the "Pixel Isometric 16x16" pack - `Structures.png`/`Tiles2.png`) had each been scaled independently via the alpha-bbox pass above: House at 2.327x, Tree at 2.13x, an ad hoc ~9% mismatch since neither was derived from a shared per-pack ratio (their crops are hand-placed illustrations, not tiles on a strict grid - only `Tiles.png`'s repeating dirt/rock cubes actually sit on this pack's namesake 16x16 grid; `Structures.png`/`Tiles2.png` don't).

Unified both to **4x** - `House.tscn`/`Tree.tscn` `Sprite2D.scale`. Chosen to match the multiplier already used for `Character`/`CombatUnit` (the Tiny Pixel Art Entities sheet, also scaled 4x), so every "16px-class" non-ground-tile sprite in the game now shares one convention. This is distinct from - and shouldn't be confused with - the ground tile's own `8x` (`iso_ground.gd`'s `TILE_SCALE`), which is a strict derivation matching a literal 16x8 diamond crop to the 128x64 world tile; House/Tree have no equivalent single native tile to derive from.

Verified safe for grid alignment before changing: `Sprite2D.offset` is defined in local, pre-scale pixel space and both scenes' offsets already equal `-anchor_pixel` (confirmed for Tree by measuring the sprite's alpha bbox row-by-row - the trunk narrows to a single contact point at the very bottom, not a flat square, and `offset` lines up with it exactly). Since `world_anchor_position = node.position + scale * (offset + anchor_pixel)`, that product is zero regardless of `scale`'s value - so changing only the scale number, without touching `offset` or the crop region, cannot drag either sprite's grid anchor. `House.tscn`'s `Label` offsets were rescaled by the same ratio (4.0/2.327 ≈ 1.719) to keep the nameplate in the same relative position on the bigger sprite; its `CollisionShape2D` was left untouched since that box is sized to the building's 2x2 grid footprint, not the sprite's pixel dimensions.

QC'd by spinning up a throwaway verification scene (House + Tree + a villager on a patch of `IsoGround`, screenshotted via `flatpak run org.godotengine.Godot --path . <scene>`, deleted after - same pattern as the original `_verify_house.tscn` pass above). House and Tree now read as a consistent, proportionate pair. **New finding, not yet addressed:** the villager now looks noticeably small standing next to House - a pre-existing mismatch between this pack's real-world scale and the Tiny Pixel Art Entities sheet's, made more visible now that House rendered bigger. Both packs happen to use the same "4x" number for unrelated reasons, which doesn't guarantee matching absolute size. Worth a follow-up pass if/when villager-vs-building proportion matters - not done here since it's a separate pack (Character/CombatUnit) the user didn't ask to touch this round.

## Follow-up (2026-07-17) - Character/CombatUnit crop tightened (scale still 4x)

Chased the villager-looks-small finding above. `Character`/`CombatUnit` share one sheet (`Tiny Pixel Art/IsometricTRPGAssetPack_Entities.png`, 16x17px grid cells) and were already perfectly consistent with each other (identical `scale=4`, identical cell size, identical `offset`, identical frame-building code) - so there was nothing to reconcile between the two. ## Bug found (2026-07-17) - Workstation's pulse tween collapsed built sprites to 1x

Reported: the completed (not construction-site) Lumber Camp looked much smaller than intended. Root cause was the *third* occurrence of the same bug class `Tree._full_scale`/`CombatUnit._full_scale` already exist to guard against: `Workstation._start_pulse()`/`_stop_pulse()` (the "looping pulse tween on an active workstation" mentioned in `CLAUDE.md`) tweened `sprite.scale` toward hardcoded `Vector2(1.08, 1.08)`/`Vector2.ONE` - harmless back when every building's `Sprite2D` was authored at an implicit 1:1 scale (the old SVGs), but the moment a post with a *real* authored scale (LumberCamp's 4x, or any of the other reskinned buildings) gets its first worker, `add_worker()` -> `_start_pulse()` runs and the tween permanently snaps the sprite down toward actual scale 1 instead of its real baseline. LumberCamp surfaced it first only because it's usually the first building to get a worker in a new game - every other `Workstation` subclass (Farm, Brickmaker, StoneMine, Workshop, TrainingGround) had the identical latent bug.

Fixed the same way as the other two: added `Workstation._full_scale`, captured from `sprite.scale` in `_ready()` (before pulsing ever starts), and `_start_pulse()`/`_stop_pulse()` now tween toward `_full_scale * 1.08`/`_full_scale` instead of the hardcoded absolutes. Verified by scripting `add_worker()` directly on a LumberCamp and reading `Sprite2D.scale` after a full pulse cycle - oscillates around the real 4.0 baseline now instead of collapsing to 1.0, confirmed visually too (teepee stays full-size with a worker shown as "1/1").

**Worth remembering for any future tween-based scale animation on a sprite that isn't authored at 1:1**: grep for `Vector2.ONE` / `Vector2(1, 1)` / `Vector2(1.0, 1.0)` used as a scale-tween target before assuming a new "looks too small" report is a fresh bug - this exact pattern has now recurred three times (Tree's grow/hit-punch, CombatUnit's hit-punch, Workstation's pulse).

**Flagged explicitly before implementing, confirmed after via screenshot:** this is a hygiene fix, not a size fix - scale x content-pixel-count is invariant to how much transparent padding surrounded that content, so cropping tighter while holding scale at 4 cannot and does not change how big anything renders (verified pixel-identical to the pre-crop screenshot; villager and Shieldbearer both still anchor correctly, feet planted on their tile, no regression). The villager-vs-House size gap from the entry above is therefore still open if it ever needs solving - that would require an actual scale increase (the 8-10x comparison rendering is the reference point if picked back up), which is a separate, bigger call since it also resizes every CombatUnit on the battlefield.
