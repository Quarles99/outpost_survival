## Prototype (2026-07-15)

Standalone test scene at `scenes/combat/CombatTest.tscn` (run directly via F6, not reachable from the main game) - two teams auto-spawn and fight per "classic RTS combat minus direct player control." Press R to respawn/restart the battle. See [[Combat Units]] for the per-type stats/behaviors it implements.

`CombatTestManager` (`scripts/combat/combat_test_manager.gd`) spawns a fixed 3 Swordsman / 2 Archer / 1 Mage roster per side, tracks each team's live roster, and declares a winner once one side is wiped. `CombatUnit` (`scripts/combat/combat_unit.gd`) does per-unit targeting (priority order per type, nearest-enemy fallback), movement, melee/ranged attacks with a defender/attacker damage-multiplier matrix, and kiting (ranged types retreat from a nearby Swordsman instead of attacking that tick). All stats are first-pass, not tuned via playtesting.

**Deliberately not built yet** (the "advanced AI" pillar above is only partially covered):
- Swordsman "block other melee units" / "push ranged units" formation behavior - units currently just walk straight at their chosen target, no group positioning.
- Any adaptive tactic-switching beyond the fixed target-priority table (e.g. retreating when losing, focus-firing a low-health target, regrouping).
- Integration with the real citizen/job system - per an explicit decision, citizens will eventually get a combat role by being assigned to a combat building the same way any other job works (see [[Combat Units]]), training a combat skill there. `CombatUnit` is a standalone prototype class for iterating on AI/damage feel in isolation; it isn't wired into `Character`/`Base`, and its stats/logic are expected to migrate into a `Character` work loop once that integration happens, not stay a separate class.

Verified headless via a temporary SceneTree script (removed after use, per this project's usual verification pattern) that ran a full battle and printed the outcome: caught and fixed a real bug where `CombatUnit._retarget()` reassigned its own `enemies` field to a filtered copy, detaching it from the shared array `CombatTestManager` prunes on death - later calls could then cast a freed reference and crash. Fixed by never reassigning `enemies` itself; filtering now happens into a local list on every use. Re-verified with several full-battle runs afterward with no errors, each resolving in ~14s.

**Main menu access (2026-07-15):** added a "Battle Test" button to `scenes/menu/MainMenu.tscn` (`scripts/main_menu.gd`) that jumps straight into `CombatTest.tscn`. Since the sandbox had no way back out, also wired Esc (`ui_cancel`) in `CombatTestManager` to return to the main menu, and updated the on-screen hint to show both `R: Restart battle` / `Esc: Main menu`.

**Formation (2026-07-15):** each team now spawns in two ranks instead of one flat line - Swordsmen up front (`FRONT_RANK_X`, 380px from center), Archers/Mage held back (`BACK_RANK_X`, 520px from center), per an explicit request for a more tactical starting arrangement. `CombatTestManager._spawn_team` splits the roster into a front line (Swordsmen) and back line (everything else) and spawns each as its own centered row via a new `_spawn_rank` helper. The 140px rank gap is deliberately smaller than Archer/Mage's attack_range so the back line can often open fire without advancing at all, though it isn't tuned to guarantee that in every spread. This is still just starting positions - no ongoing formation-keeping (units break rank immediately once they start moving/kiting), which is the same "no group positioning" gap already noted above for Swordsman blocking/pushing.

**Real pathfinding + avoidance (2026-07-15):** after the kiting-math fix above still left archers reported as "stuck until the swordsman dies," diagnosed that the actual root cause was two different bugs stacked together, and only one of them was a routing/pathfinding problem:
1. The kiting retreat only put 60% of an Archer's speed into pure separation (the rest went into curving toward its target) - since Archer speed (100) x 0.6 = 60 was *less* than a pursuing Swordsman's speed (90), the Swordsman could out-position the retreat entirely regardless of direction, so no steering fix alone could have solved it.
2. Even fixing (1), a fleeing/approaching unit had no way to route around a unit directly in its path - "go the way that's clear" needs actual agent-vs-agent collision avoidance, which a hand-rolled direction blend can approximate for one specific threat but doesn't generalize.

Rather than keep iterating on hand-rolled steering math, added real navigation: a procedurally-baked `NavigationRegion2D` (open rectangle covering the field - no obstacles in this sandbox, so nothing to parse, see `CombatTestManager._setup_navigation()` using the modern `NavigationServer2D.bake_from_source_geometry_data()`, not the deprecated `NavigationPolygon.make_polygons_from_outlines()`) plus a `NavigationAgent2D` per unit with `avoidance_enabled = true` (RVO local collision avoidance). Verified the avoidance mechanism works standalone first (temporary probe script, removed after use): confirmed a moving agent visibly curves around a stationary blocking agent rather than passing through it.

This changed the division of labor in `CombatUnit._process()`: the "desired velocity" a unit computes (flee straight away from a threat, or head toward its target via `NavigationAgent2D.get_next_path_position()`) is now just a *preference* fed into `nav_agent.set_velocity()` - the nav agent's avoidance simulation is what actually routes around whatever's in the way (the fleeing case no longer needs the tangent-blend hack from the previous fix, since routing is no longer this class's problem to solve by hand; kiting reverted to a straightforward full-speed retreat, which alone fixes bug (1) above since 100 > 90 now applies at full strength). `_on_velocity_computed()` applies the async-computed safe velocity once NavigationServer2D delivers it.

Verified headless (temporary SceneTree scripts, removed after use): 5 full battles all resolved cleanly in 36-37s with no deadlocks or errors, and a detailed per-unit trace confirmed continuous target-reassignment/damage exchange throughout rather than any unit stalling indefinitely. Battles now take roughly 2x longer than before this change (was ~14-19s) - the approach phase is visibly slower/more crowded, a known RVO artifact when several agents converge on the same area at once (their preferred velocities conflict and avoidance yields ground to resolve it). Not tuned further (`neighbor_distance`/`time_horizon_agents`/agent `radius` are all NavigationAgent2D defaults) - a first pass to fix the actual reported bug, not a pacing/balance pass.

**Speed + avoidance tuning (2026-07-15):** reported as too slow, and Swordsmen specifically looked like they were "running away to the edges of the map" instead of engaging - the second one shouldn't be possible from `CombatUnit`'s own logic (Swordsman never kites, `avoids_melee` is false for it, so its only two branches are "approach target" and "stand and attack"), which pointed at the avoidance layer itself rather than unit AI: RVO's default tuning (`neighbor_distance` 500, `time_horizon_agents` ~20s) is sized for large crowds reacting to far-off traffic, so with only ~12 units total, every unit was factoring in nearly the whole battle as "nearby" and throwing wide preemptive detours around the whole scrum - explains both symptoms at once (the detours themselves read as slow, and a bad one can genuinely walk a unit toward open ground since RVO reasons about nearby agents only, not the navmesh's own bounds).

Three changes:
1. Move speeds raised meaningfully (Swordsman 90->150, Archer 100->170, Mage 85->140 - kept the same relative ordering/gaps, scaled to roughly match `Character.MOVE_SPEED` (140) elsewhere in the project rather than picking new numbers in a vacuum).
2. `nav_agent.neighbor_distance` dropped to 200 and `time_horizon_agents` to 2.0 (both set in `CombatUnit.setup()`) so avoidance only reacts to genuinely close, near-term collisions - tight local dodges instead of wide preemptive arcs.
3. Added a hard position clamp as a safety net regardless of how avoidance is tuned: `CombatTestManager` now passes its `NAV_BOUNDS` (inset by `CombatUnit.UNIT_RADIUS`) into each unit's `setup()` as `play_bounds`, and `_on_velocity_computed()` clamps `global_position` into it every frame - RVO has no inherent awareness of map edges, so this is the actual backstop against "runs to the edges," not just the tuning above.

Verified headless: 3 full battles resolved in 18-23s (back in line with the pre-navigation ~14-19s baseline, not the 36-37s the untuned avoidance produced), and the max distance any unit reached from the map center across those runs (528-710) stayed well inside `NAV_BOUNDS` - the clamp never had to visibly engage, meaning the retuned avoidance fixed the edge-running at the source rather than merely papering over it.

**Hold the line while engaged (2026-07-15):** reported that Swordsmen kept visibly drifting/moving around even after closing to melee range and starting to fight, instead of planting themselves and finishing that target. Root cause: `nav_agent.set_velocity(Vector2.ZERO)` only sets a *preferred* velocity - RVO avoidance treats separation from crowded neighbors as a hard constraint regardless of what an agent prefers, so a unit standing still mid-fight, packed in among allies also converging on the front line, could still get physically jostled by everyone else's avoidance resolving around it. A zero preference was never a guarantee of zero movement.

Added `CombatUnit._holding_position` (true whenever a unit is in range of `_target` with no threat to evade - the same "stand and fight" branch in `_process()`), checked by `_on_velocity_computed()` to skip applying avoidance's suggested nudge entirely while true. An engaged unit still calls `set_velocity(Vector2.ZERO)` every frame, so it keeps registering its position with the avoidance simulation and stays a proper obstacle for everyone else's routing - it just can't be pushed around by that simulation anymore itself. This generalizes past Swordsman specifically: any unit type reaches the same "stand and fight" branch once in range with nothing to flee (a stationary Archer/Mage mid-volley holds still too, for the same reason).

Verified headless: instrumented every unit's position each frame while `_holding_position` was true across 3 full battles (~9,300-10,500 sampled frames per run) and confirmed zero drift (`max_drift_while_holding` exactly 0.0 in all three) - engaged units now hold perfectly still until their target dies, at which point normal retargeting/movement resumes.

**Formation entity + weighted leash, Phase 1 (2026-07-15):** the previous fix didn't actually solve the reported issue - Swordsmen were still, per the user, "running towards the edge of the map away from any enemy" a significant fraction of the time once outnumbered. A headless trace of the actual mechanism showed it wasn't a bug at all: a Swordsman (150 speed) chasing a kiting Archer (170 speed) can never close the gap in a straight-line race - the Archer is simply faster, so the "chase" just drags both units across the whole map together until something else resolves it.

A hard-clamped leash to each unit's own static spawn point (first attempt) was worse: it caused 2 of 6 headless battles to *deadlock* (never resolve in 90s), since two units each leashed to their own far-apart, never-updating point could end up with no reachable overlap. The user proposed something smarter mid-session: a dynamic `Formation` entity units leash to their *place in*, plus (in a follow-up note) that leashing should be a growing weighted consideration, not a hard range. Full design in `Planning/Formation System (Combat Sandbox)` (now closed) and the Claude Code plan file it references.

Landed: `scripts/combat/formation.gd` (`Formation`, one per team) and `scripts/combat/formation_catalog.gd` (`FormationCatalog`, one "line" preset so far, mirroring `BuildingCatalog`'s convention). Each `CombatUnit` now has a `formation`/`slot_offset` instead of a static spawn point; `_apply_formation_pull()` blends combat intent with a "return to slot" pull that grows smoothly with distance (full pull at `FORMATION_LEASH_RANGE`, none at the slot itself) rather than a hard positional clamp.

Getting the anchor's own movement rule right took three failed iterations, each caught by a headless trace before landing on anything:
1. **Advance-toward-enemy + drift-clamp-to-centroid** - the two rules fought each other into a stable equilibrium well short of contact (the anchor visibly advanced for a few seconds, then froze in place for an entire 90s battle - zero deaths, since leash centers stopped tracking the fight at all).
2. **Anchor = raw living centroid** (dropping rule 1's "advance" entirely, letting the team's own forward movement carry the anchor) - looked promising in isolation, but a full trace showed a *worse* pathology: a Swordsman with target distance steadily *increasing* (backing away from its own target for the entire trace). Root cause: including actively-fleeing Archers/Mages in the centroid let their (correct, intentional) kiting drag the whole team's average position backward, which pulled every other unit's leash backward too, compounding into the entire team retreating. Fixed by excluding `_fleeing` units from the centroid average - didn't help.
3. **The actual bug**, found after (2) still reproduced identically: a reference-frame mismatch, not a feedback loop. `slot_offset` is computed assuming the formation's own position is the center both ranks sit relative to, but the *raw* average position of an asymmetric roster (3 units at depth 380, 3 at depth 520) naturally sits at the weighted depth (~450), not 0 - so a perfectly-formed team's own raw centroid was never actually at the point its slot offsets were computed relative to. Every unit's leash center jumped ~450px off on the very first frame and compounded from there. Fixed by averaging `position - slot_offset` (each unit's own offset "undone" before averaging) instead of raw position - a perfectly-formed team's centroid now lands exactly back on the formation's position, matching what `assign_slots()` assumes.

Verified headless after the fix: a position trace showed the expected shape (steady, monotonic approach to the target, holding exactly flat once in attack range) instead of a runaway; 13 full battles across two verification passes resolved with zero deadlocks/timeouts (17-49s, in line with or better than pre-Formation baselines). One run took 49s with a unit reaching `max_dist_sword=1105` (near the map edge) before still resolving normally - consistent with, not a violation of, the "weighted consideration, not a hard wall" design: some overshoot is expected by construction, it just has to actually resolve, which it did in every run.

**Strategist AI + asymmetric matchups (2026-07-15):** built out the deferred vision from [[Formation Strategy AI]] - a per-team `StrategistAI` (`scripts/combat/strategist_ai.gd`) that dynamically switches its team's `Formation` mid-battle to counter whatever the enemy's composition actually is. Decisions screened to the user before building: full mid-battle switching (not just a pre-battle pick), full information (no scouting/fog-of-war model), and rule-based counter-picking (not a general scoring/utility AI) - explainable and debuggable over a first pass.

Three new `FormationCatalog` presets, each a genuine counter-pick derived from `DAMAGE_MULTIPLIERS` rather than arbitrary variety: **Rush** (tight, fast-closing, barely kites - counters Archer-heavy enemies by minimizing exposure time while closing), **Skirmish** (wide, holds ranged units far back, kites aggressively - counters Swordsman-heavy enemies), **Guard** (Archers/Mages placed *forward*, Swordsmen held back - counters Mage-heavy enemies, since Archers/Mages resist Magic while Swordsmen are weak to it; a concrete case of the multiplier table driving a non-obvious formation shape). `formation.tactics.get("melee_avoid_radius", ...)` is now actually read by `CombatUnit._nearest_melee_threat()` (previously an unused extension point) so each preset can override how evasive its ranged units are, not just their starting layout.

`StrategistAI.update()` re-evaluates every 4s (a separate 6s switch cooldown prevents thrashing near a decision boundary): tallies living enemy HP by type, picks whichever preset counters the type with the highest total HP, and calls `Formation.apply_preset()` if that differs from the current choice. Reassigning slots doesn't need any teleport/transition logic of its own - the existing weighted-pull leash (from the earlier fix above) already makes units drift to a new slot gradually, so "the formation reorganizes over real time" fell out of infrastructure that already existed for an unrelated reason.

`CombatUnit.point_cost(unit_type)` (derived from existing stats: `health * damage/attack_interval`, not a separate hardcoded number) backs three named test matchups in `CombatTestManager.MATCHUPS` (press M to cycle) at roughly comparable total cost but different composition - `melee_vs_ranged` (Archer-heavy vs Swordsman-heavy) and `mage_heavy` (Mage-heavy vs balanced) alongside the original mirror-match roster as a control. A `StrategyLabel`/`MatchupLabel` on the HUD show what's currently active.

Verified headless across 3 full passes (9 battles: all 3 matchups x 3 runs) with zero deadlocks/timeouts. Confirmed the counter-picking is real, not cosmetic: in `melee_vs_ranged`, the Archer-heavy side picked Skirmish (correctly identifying the enemy's Swordsman-heavy composition) while the Swordsman-heavy side independently picked Rush (correctly identifying the Archer-heavy enemy) - two different rosters producing two different, composition-appropriate strategies, unprompted. Also confirmed genuine mid-battle adaptation: in `mage_heavy`, the balanced side switched Guard -> Rush at t=32s as the enemy's Mages died off and Archers became the new dominant threat by remaining HP.

**Post-verification bug, from live play feedback:** reported that Skirmish-mode ranged units were staying farther back than their own attack range, unable to actually skirmish (shoot-and-retreat never got to the "shoot" part). Root cause: Skirmish's `melee_avoid_radius` was set to 280, which exceeds *both* Archer's attack_range (260) and Mage's (220) - any Swordsman close enough to be a viable target was also close enough to trigger fleeing, leaving no "safe firing zone" and no reason to ever stop retreating. Fixed by lowering it to 200 (under both ranges, still notably more evasive than the 150/170 per-type defaults). Verified headless: 58 attacks landed by Team A's Archer/Mage while in Skirmish formation across a single 23.6s battle (0 before the fix, by construction of the bug), consistent across 3 repeat runs; the full 3-matchup suite also re-verified clean afterward with faster resolution times (17-26s vs the earlier 23-60s range) - consistent with ranged units actually fighting instead of perpetually retreating.

**Deferred still**: additional formation presets beyond the four here, any player-facing formation-choice UI (the `BuildMenu`/`RecruitPanel` signal-based option-picker pattern is confirmed reusable, per [[Formation Strategy AI]]), and a more general scoring/utility AI (explicitly not chosen over rule-based counter-picking for this pass).

**Outrider + Trapper (2026-07-15):** two new unit types added to give the triangle an answer to kiting Archers/Mages simply outrunning a Swordsman forever - see [[Combat Units]] for the full stat/design writeup (both flat 1.0x in `DAMAGE_MULTIPLIERS`, so they don't touch the existing triangle's balance). `FormationCatalog`/`StrategistAI` both extended to place and counter-pick them (Trapper joins the front rank, Outrider stays back-rank-default; `COUNTER_PRESET` maps Outrider-dominant -> Rush, Trapper-dominant -> Guard). New "fast_movers" test matchup added to `CombatTestManager.MATCHUPS`. Verified headless: the new `CombatUnit.apply_slow()`/`_speed_multiplier` debuff system visibly applies and decays correctly, and the full (now 4-matchup) suite still resolves cleanly with no regressions.

`fast_movers` (solo Trapper vs. Outrider) turned out to be testing the wrong pairing - Trapper losing that 1v1 isn't a bug, per an explicit clarification it's meant to be a support unit for Archers, not an Outrider duelist. Added a second matchup, `support_vs_outrider` (3 Trapper/4 Archer vs. 6 Outrider), and verified across 5 runs that the intended composition does win decisively (12.5-13.75s, minimal losses) - see [[Combat Units]]'s own note for the full before/after.
