# Village Raids (Orc Raiders)

Live, in-place combat on the actual village map - orcs patrol from a nightly arrival point, may catch and scatter a working citizen, and the player can rally the town's trained garrison to fight them right where they stand. Deliberately a separate system from [[Combat System]]'s existing "Simulate Attack" debug flow (scene-swap to `CombatTest.tscn` via `BattleState`) - that flow is untouched, still a dev/test tool. See `Outpost_Survival/Actionable Ideas/Completed/Implement orc enemies present on the village map..md` for the original request and implementation write-up.

## How it works

**Spawning.** `Base._on_night_started_raid()` listens to `DayNightCycle.night_started` and spawns a small raiding party at a random map-edge cell (`WorldGrid.find_random_edge_cell()`) each qualifying night - only one raid active at a time. Composition and orc skill level scale with how many nights have passed (`OrcRaider.roster_for_night`/`skill_level_for_night`) - see [[Balance]]'s "Village Raids" section for the exact numbers, explicitly flagged there as a first pass needing playtesting.

**Patrol AI.** `OrcRaider` (`scripts/combat/orc_raider.gd`) `extends CombatUnit` and adds a `Mode` state machine (`PATROL` / `ALERTED` / `ENGAGED`) layered *around* the inherited class rather than modifying it. While `mode != ENGAGED`, `_process()` runs a lightweight per-frame wander/notice loop instead of calling into `CombatUnit`'s own `_process()` - it never touches `_target`/`_retarget()`/`_attack()`, since `CombatUnit._target` is typed `CombatUnit` and can never point at a `Character` anyway. An orc wanders within `PATROL_RADIUS` of its arrival point, and every `NOTICE_INTERVAL` scans nearby citizens, rolling `ATTACK_CHANCE` to go `ALERTED` and approach the nearest one. Catching up to them calls `Character.flee_home_from_raid()` and returns to `PATROL`.

**Villager consequence.** Deliberately *not* a wound/HP system - `Character` has no HP/damage fields at all today, and adding one wasn't judged a prerequisite for this to feel consequential. `flee_home_from_raid()` interrupts whatever the citizen was doing and sends them home; `assigned_post` is left untouched (a temporary interruption, not a departure), so the only cost is lost production and an idle citizen standing around until the next dawn recalls them (`Base._recall_fled_citizens()`, called from `_on_day_started`).

**Rally.** Clicking any orc (`Base._on_orc_selected`) enables HUD's Rally button. Pressing it (`Base._on_rally_pressed`) reuses `_gather_soldier_squad()` - the exact same "every citizen currently on `TrainingGround` duty" roster `_on_attack_pressed`'s sandbox deployment already computes - hides each soldier `Character` (`visible`/`input_pickable = false`, work stopped, `assigned_post` still untouched) and spawns a normal `CombatUnit` avatar in their place at their last position. A `Formation` is built for the squad the same way `CombatTestManager._spawn_battle` builds one for a sandbox team; `RaidController.begin_engagement()` wires both rosters' `enemies` cross-references, gives every orc a real `formation_b` slot offset (they had none while patrolling independently), and flips every live orc's `mode` to `ENGAGED` - the single point where `super._process()` starts running, handing off to `CombatUnit`'s completely unmodified targeting/attack/morale/formation-leash AI. From here it's the same fight described in [[Combat System]], just fought on Base's own map/nav_region instead of the sandbox's.

**Resolution.** `RaidController` (`scripts/combat/raid_controller.gd`) mirrors `CombatTestManager`'s own mass-rout/empty-team bookkeeping (`_check_mass_rout`, matching `Formation.is_mass_routed()`/`force_rout_all()`) rather than duplicating a new scheme. `Base._process()` calls `_raid.update(delta)` every frame and, once `resolved` flips true, `_resolve_raid()` reuses `Base._apply_battle_result()` **verbatim** - the exact same casualty-removal-via-`_character_leaves` + outcome-message shape a real sandbox deployment already uses - then `_teardown_raid()` frees every orc/soldier-avatar node and both Formations and restores any surviving hidden soldier (`visible`/`input_pickable` + `assign_to(assigned_post)` to resume work). A raid still unresolved at dawn is force-ended the same way (`_force_end_raid_at_dawn`, called from `_on_day_started`) - orcs "withdraw," any casualties that already happened are still applied, outcome reported as a draw.

**Save/load.** A raid is never persisted - `_teardown_raid()` runs unconditionally at the top of `_apply_state()`, so a load mid-raid always reverts cleanly to "no raid in progress" (orphaned combat nodes freed, any hidden soldier restored) rather than resuming or crashing. This is a deliberate, documented limitation, not an oversight - in-progress raid state is discarded, never persisted.

## Deferred

- Multi-select/box-select of soldiers or orcs - Rally is one-click, whole-garrison-at-once by design; marquee-select doesn't exist anywhere in this codebase.
- Patrol *formations* for orcs (loose independent wandering only; real formation structure only appears once Rally is pressed).
- Citizen flee/hide AI beyond "walk home and stop" - no pathing to a specific safe building, no group panic behavior.
- A real citizen-HP/wound system - concluded unnecessary for this to feel consequential; revisit only if actually needed later.
- "Drop what they were carrying" loot on attack - `Character` has no held-item/inventory state to drop.
- Orc camps/bases as a placeable, persistent threat source - raids are a nightly pop-up event tied to `DayNightCycle`, not a map feature.
- Orc-specific art - reuses `CombatUnit`'s existing `UnitType` sprite rows + Team B's tint, same as every sandbox enemy.
